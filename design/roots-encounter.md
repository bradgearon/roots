# Roots Encounter Protocol — REP/1 experimental Android profile

A Post continuously advertises one connectable BLE service. A passing Roots device discovers the service using a low-power filtered scan, reads the dynamic LE L2CAP PSM from a GATT characteristic and opens a bidirectional Bluetooth LE connection. No IP, access point, Internet service, Bluetooth bonding or LAN invitation is needed. A Post can also be an Android phone.

## Publication and authorization

Open Exchange is enabled by default, with one-time disclosure and OS permission. Each phone advertises and scans automatically. All explicitly published knowledge topics are then eligible for both directions and for forwarding. There is no per-encounter confirmation or topic gate. The UI must clearly state that copies may leave the device permanently. The native Tree's current LAN graph catalog includes raw captures and is not an appropriate public catalog: REP/1 reuses the explicit Mesh publication catalog only. A future public graph projection can publish user-authorized graph relationships and source links without exporting the raw captured Tree. Received content is untrusted and is not runtime authority.

## Radio

Service UUID 7d6f6f74-732d-4c45-9a01-000000000001; readable PSM characteristic 7d6f6f74-732d-4c45-9a01-000000000002. PSM is two unsigned big-endian bytes, dynamic for the lifetime of the listening socket. Use LE CoC (not classic RFCOMM); reject missing, zero or out-of-range PSM. Advertisement contains only the service UUID, no user identifier, MAC binding, topic or data. The Android profile starts with Android 12+ and a user-started connectedDevice foreground service; Android and device power-management policies still apply. GATT-only fallback, passive PendingIntent scanning and firmware are future work. Restore enabled and authorized service on normal boot/update and foreground resume; no restart after a user force-stop until Android allows it. No wake lock, exact alarm, Internet permission addition or Wi-Fi routing.

## Wire contract (prototype, not frozen)

On the byte stream use big-endian 32-bit lengths. Client sends a hello then server sends a hello, each limited to 1024 bytes. Hello: 32-bit magic 0x52455031, length-prefixed X.509 SubjectPublicKeyInfo persistent P-256 signing key, length-prefixed ephemeral P-256 key, 32-byte random nonce. Hash SHA-256 of ASCII Roots REP/1 handshake and length-prefixed client and server hello, in order. Each side signs role byte (1 client, 2 server) plus transcript hash with SHA256withECDSA. Exchange length-prefixed signatures (max 256 bytes), client first. Verify both proofs before any knowledge. ECDH on ephemeral keys; HKDF-SHA256 extract using transcript hash as salt, expand ASCII Roots REP/1 client to server or Roots REP/1 server to client plus 0x01, 32 bytes each. AES-256-GCM, nonce 4 zero bytes plus big-endian uint64 sequence starting at zero for each direction; AAD handshake label plus nonce. Encrypted frame length includes 16-byte tag; plaintext 1–65536 bytes. Terminate on any failure. This is experimental composition, not Noise/TLS compliance and not independently audited. A first-contact self-authenticated identity does not prove ownership of a named physical Post or protect against identity substitution at first contact; only a previously known key can be recognized. No stable personal identifier in advertisement; peer-visible signing identity is linkable across encounters. Private keys remain Android Keystore backed.

Inside encrypted records, use UTF-8 JSON in the first implementation to reuse MeshItem canonical content hashes; CBOR is a later version. Client sends bind, server answers bound. Client pulls and releases, then server pulls and releases. Each pull issues inventory with saved root and after cursor; responder returns root (SHA-256 of sorted concatenated 64-character content IDs), up to 32 sorted IDs and more flag. Different root resets cursor. Request want with an offered id, answer data with exact verified MeshItem JSON, ack only after durable Tree store. Release ends a direction. Each direction bounded to 64 examined IDs, eight fetched items and three inventory requests; timeout closes the connection. On reconnect, durable cursor resumes after verified items; end of inventory resets cursor for subsequent cycles. Each peer's .axon stores peer public-key digest, public wildcard scope, remote root, cursor and encounter count under app-private noBackup storage. No coordinates, MAC or private runtime grant. Tree clear cancels active sync; subsequent cycles recheck missing items.

## Qualification before merge

Two phones with Bluetooth on and Wi-Fi/cellular off, one Publisher and one Passerby, each with a distinct explicitly published remembrance. Verify bidirectional delivery, same-source link retained, repeat encounter after process restart, resume after breaking radio, no duplicate Tree observations, no private raw captures or LAN invitation credentials sent, and stop/revoke. Test Bluetooth disabled, denied permissions, screen off, oversized or malicious data, corrupted records, repeated reconnects, key mismatch, full binding store. Benchmark discovery latency, power draw, airtime and publisher concurrency on real hardware. Independent cryptography review and firmware interoperability are required; no production security or battery-life claim.

## Android app entry point

On first normal Roots launch the desired state is ON. Explain reciprocal public publication exchange and request the Android Nearby Devices permissions once; no per-encounter or role-selection prompt. If permission is denied, retain the desired state but stay inactive, with a manual permission action in Roots Mesh > Manage nearby exchange. Turning off persists the preference and stops radio activity. Notification Turn off is equivalent. Boot/update receiver and app resume restore an authorized enabled service. Bluetooth off pauses the radio while preserving the desired state; Bluetooth on and transient radio errors trigger event-driven recovery with bounded backoff.

Every capable phone both scans and advertises. Separate inbound/outbound workers allow concurrent radio discovery with one bounded exchange at a time. Existing hardware Posts can expose only the PSM. Automatic phones additionally expose COORD UUID 7d6f6f74-732d-4c45-9a01-000000000003 (eight random per-radio bytes, not a stable ID); prefer the smaller unsigned rank as initiator, with occasional reverse attempts and randomized retry to tolerate asymmetric scanning. Older clients still read the two-byte PSM. Self bindings are rejected cryptographically. No wireless address is stored. Quiet successful contacts receive a longer retry cooldown. Devices without BLE advertising can still scan.

The connection view shows saved bindings, online exchange versus offline, first/last encounter, lifetime sent/received totals, local labels, and recent session outcomes (up to 200, no payloads or coordinates). Block persists by authenticated peer key and rejects further exchange, including aborting an active session; unblock restores automatic exchange. Clear history does not remove bindings or totals. Session counts reflect acknowledged outbound and committed inbound items; an abrupt process death before the final outcome can leave counters incomplete. Existing LAN Axon policy remains separate.

Qualification: two default-enabled phones, permission once, no role selection, Wi-Fi and cellular off; confirm both directions and persistent binding. Test toggle off/on and restart, Bluetooth off/on, screen off, app background, reboot, simultaneous discovery, block during transfer and re-encounter, clear history, label persistence. Verify no repeated permission prompts or raw capture publication, and no per-device location tracking. Android can throttle or terminate a foreground service and cannot restart a force-stopped app until allowed. Power and reliability require physical tests.

Prototype limits: one encounter at a time, no GATT-only fallback, dedicated Post firmware or iOS implementation; explicitly published legacy records only, not the full graph projection. Cryptographic review and device tests are required before merge.
