# Roots Encounter Protocol — REP/1 experimental Android profile

A Post continuously advertises one connectable BLE service. A passing Roots device discovers the service using a low-power filtered scan, reads the dynamic LE L2CAP PSM from a GATT characteristic and opens a bidirectional Bluetooth LE connection. No IP, access point, Internet service, Bluetooth bonding or LAN invitation is needed. A Post can also be an Android phone.

## Publication and authorization

Open Exchange is enabled by default, with one-time disclosure and OS permission. Each phone advertises and scans automatically. All explicitly published knowledge topics are then eligible for both directions and for forwarding. There is no per-encounter confirmation or topic gate. The UI must clearly state that copies may leave the device permanently. The native Tree's current LAN graph catalog includes raw captures and is not an appropriate public catalog: REP/1 reuses the explicit Mesh publication catalog only. A future public graph projection can publish user-authorized graph relationships and source links without exporting the raw captured Tree. Received content is untrusted and is not runtime authority. Received public records are committed to a separate external publication database; only a user-approved import copies a record into the private Tree.

## Radio

Service UUID 7d6f6f74-732d-4c45-9a01-000000000001; readable PSM characteristic 7d6f6f74-732d-4c45-9a01-000000000002. PSM is two unsigned big-endian bytes, dynamic for the lifetime of the listening socket. Use LE CoC (not classic RFCOMM); reject missing, zero or out-of-range PSM. Advertisement contains only the service UUID, no user identifier, MAC binding, topic or data. The Android profile starts with Android 12+ and a user-started connectedDevice foreground service; Android and device power-management policies still apply. GATT-only fallback, passive PendingIntent scanning and firmware are future work. Restore enabled and authorized service on normal boot/update and foreground resume; no restart after a user force-stop until Android allows it. No wake lock, exact alarm, Internet permission addition or Wi-Fi routing.

## Wire contract (prototype, not frozen)

On the byte stream use big-endian 32-bit lengths. Client sends a hello then server sends a hello, each limited to 1024 bytes. Hello: 32-bit magic 0x52455031, length-prefixed X.509 SubjectPublicKeyInfo persistent P-256 signing key, length-prefixed ephemeral P-256 key, 32-byte random nonce. Hash SHA-256 of ASCII Roots REP/1 handshake and length-prefixed client and server hello, in order. Each side signs role byte (1 client, 2 server) plus transcript hash with SHA256withECDSA. Exchange length-prefixed signatures (max 256 bytes), client first. Verify both proofs before any knowledge. ECDH on ephemeral keys; HKDF-SHA256 extract using transcript hash as salt, expand ASCII Roots REP/1 client to server or Roots REP/1 server to client plus 0x01, 32 bytes each. AES-256-GCM, nonce 4 zero bytes plus big-endian uint64 sequence starting at zero for each direction; AAD handshake label plus nonce. Encrypted frame length includes 16-byte tag; plaintext 1–65536 bytes. Terminate on any failure. This is experimental composition, not Noise/TLS compliance and not independently audited. A first-contact self-authenticated identity does not prove ownership of a named physical Post or protect against identity substitution at first contact; only a previously known key can be recognized. No stable personal identifier in advertisement; peer-visible signing identity is linkable across encounters. Private keys remain Android Keystore backed.

Inside encrypted records, use UTF-8 JSON in the first implementation to reuse MeshItem canonical content hashes; CBOR is a later version. Client sends bind, server answers bound. Client pulls and releases, then server pulls and releases. Each pull issues inventory with saved root and after cursor; responder returns root (SHA-256 of sorted concatenated 64-character content IDs), up to 32 sorted IDs and more flag. Different root resets cursor. Request want with an offered id, answer data with exact verified MeshItem JSON, ack only after durable external publication store. Release ends a direction. Each direction bounded to 64 examined IDs, eight fetched items and three inventory requests; timeout closes the connection. On reconnect, durable cursor resumes after verified items; end of inventory resets cursor for subsequent cycles. Each peer's .axon stores peer public-key digest, public wildcard scope, remote root, cursor and encounter count under app-private noBackup storage. No coordinates, MAC or private runtime grant. Tree clear cancels active sync; subsequent cycles recheck missing items.

## Qualification before merge

Two phones with Bluetooth on and Wi-Fi/cellular off, one Publisher and one Passerby, each with a distinct explicitly published remembrance. Verify bidirectional delivery, same-source link retained, repeat encounter after process restart, resume after breaking radio, no duplicate Tree observations, no private raw captures or LAN invitation credentials sent, and stop/revoke. Test Bluetooth disabled, denied permissions, screen off, oversized or malicious data, corrupted records, repeated reconnects, key mismatch, full binding store. Benchmark discovery latency, power draw, airtime and publisher concurrency on real hardware. Independent cryptography review and firmware interoperability are required; no production security or battery-life claim.

## Android app entry point

On first normal Roots launch the desired state is ON. Explain reciprocal public publication exchange and request the Android Nearby Devices permissions once; no per-encounter or role-selection prompt. If permission is denied, retain the desired state but stay inactive, with a manual permission action in Roots Mesh > Manage nearby exchange. Turning off persists the preference and stops radio activity. Notification Turn off is equivalent. Boot/update receiver and app resume restore an authorized enabled service. Bluetooth off pauses the radio while preserving the desired state; Bluetooth on and transient radio errors trigger event-driven recovery with bounded backoff.

Every capable phone both scans and advertises. Separate inbound/outbound workers allow concurrent radio discovery with one bounded exchange at a time. Existing hardware Posts can expose only the PSM. Automatic phones additionally expose COORD UUID 7d6f6f74-732d-4c45-9a01-000000000003 (eight random per-radio bytes, not a stable ID); prefer the smaller unsigned rank as initiator, with occasional reverse attempts and randomized retry to tolerate asymmetric scanning. Older clients still read the two-byte PSM. Self bindings are rejected cryptographically. No wireless address is stored. Quiet successful contacts receive a longer retry cooldown. Devices without BLE advertising can still scan.

The connection view shows saved bindings, online exchange versus offline, first/last encounter, lifetime sent/received totals, local labels, and recent session outcomes (up to 200, no payloads or coordinates). Block persists by authenticated peer key and rejects further exchange, including aborting an active session; unblock restores automatic exchange. Clear history does not remove bindings or totals. Session counts reflect acknowledged outbound and committed external inbound items; an abrupt process death before the final outcome can leave counters incomplete. Existing LAN Axon policy remains separate.

Qualification: two default-enabled phones, permission once, no role selection, Wi-Fi and cellular off; confirm both directions and persistent binding. Test toggle off/on and restart, Bluetooth off/on, screen off, app background, reboot, simultaneous discovery, block during transfer and re-encounter, clear history, label persistence. Verify no repeated permission prompts or raw capture publication, and no per-device location tracking. Android can throttle or terminate a foreground service and cannot restart a force-stopped app until allowed. Power and reliability require physical tests.

Prototype limits: one encounter at a time, no GATT-only fallback, dedicated Post firmware or iOS implementation; explicitly published records only, not the full graph projection. Cryptographic review and device tests are required before merge.

## Receive routing and zero-publication diagnostics

The general Receive missing knowledge button now refreshes automatic nearby Axons when the invitation field is empty and there is a saved nearby binding (or when nearby discovery is enabled and no private LAN subscription is selected). An explicit LAN invitation remains authoritative. The dedicated Receive nearby Axons now action does not require a private subscription. It clears discovery backoff so a subsequent BLE advertisement can initiate exchange; it does not claim receipt before a radio session completes. The nearby card refreshes its live status while visible.

REP/1 inventory replies optionally include total; release optionally includes more_pending. Older peers ignore the additional fields and may not report their total. The session history distinguishes a zero-publication inventory, an already-held inventory, unfinished inventory and a stage-specific interruption. Durable checkpoints are still written after each newly committed publication, but already-held IDs are checkpointed only per page. Bindings are saved after the authenticated bind operation, before transfer.

The external scope is intentionally not the private Tree graph. Publish a remembrance or explicitly publish selected original X records with exact source links and confirmed redistribution rights using Publish existing public Tree items; only their original body and source link are projected, never private understanding, author metadata or raw screen observations. A URL does not prove that a post is public. Received records remain under External knowledge until intentionally imported. Test with distinct published items on two updated devices; no subscription or LAN listener is needed. Check local publication count, remote offer count, receive total and stage if interrupted. Device builds and radio tests remain required.

## Automatic publication and main Tree retention (supersedes manual import)

Nearby publication now includes the entire eligible linked original X-post projection, without per-item selection or topic filters, when the device has approved the automatic source scope. New installs offer this scope during initial exchange consent; existing installations get one migration prompt because their previous permission covered explicitly published records only. The setting can be disabled in Manage nearby exchange. An exact link does not establish public visibility or redistribution rights; the disclosure makes this limitation explicit. Unlinked originals, private understanding, raw screen observations, author/contact metadata and credentials are never included in the automatic projection. Explicit publications remain eligible. The management view reports total local offers, automatic offers and originals missing exact links.

Incoming verified publications are committed to durable external receipt storage, then immediately retained in the main Tree with original content-addressed identity, body, topic, source link and receipt-peer provenance. The sender is acknowledged only after Tree retention. The external view is receipt history rather than a required import step. Pending receipts from previous versions or interrupted writes are reconciled on app/service startup and after encounters. Already imported receipts are not automatically resurrected on Tree clear. Main Tree cards label external references and unverified claims. A public receipt does not grant internal membership or authority. No change to LAN permissions or GPU grants. Both updated devices need eligible public data and approved automatic publication for an actual transfer. Android runtime verification remains pending.

## Root graph subscriptions (supersedes the linked-post-only scope)

Every authenticated accepted nearby binding is persisted as a wildcard local Axon subscription before catalog preparation. Existing nearby .axon files are read by the unified AxonRegistry without requiring a new binding or a LAN credential. Roots Home and Roots Mesh show the registry's counts and connection rows; private LAN remains independently authorized. Blocking keeps the saved identity but removes it from the active subscription count.

Full Root graph mode is offered once during setup or migration, with explicit disclosure that the full retained Tree may contain sensitive captured text and private notes. It must not silently expand previously restricted publication permission. Once approved, the nearby publisher pages native Tree observations and branches without source-link or topic filtering, omitting local transport credentials/receipt wrappers and malformed or oversized records. Existing explicit public records and received envelopes remain available. This mode is appropriate for a Tree that is authorized for public redistribution; for confidential community sharing use the separately authorized Internal Mesh. Both peers must support root_graph in the bind handshake to exchange graph items. Older peers get legacy publication format. Full Root protocol bounds each direction to 32 new items and 256 inventory IDs per encounter; saved sorted cursors continue despite changing inventory roots and wrap at the end. Receipt storage limit is 100,000 entries. Original graph envelopes remain in durable receipt storage; mapped main Tree records retain original grouping, content and provenance under a separate external namespace, never directly overwrite native local keys or activate remote branch definitions as local agents. Actual receipt/throughput and full graph coverage require device tests.

## Unified Receive and local bulk handoff

The bottom Receive missing knowledge action is now the single manual synchronization entry point. It resolves existing public Axon subscriptions through the unified registry; when private LAN access is selected it also invokes the existing LAN transfer engine. Explicit pasted private invitations remain authoritative. A public receive request tracks the subscribed identities, reports live inventory/transfer progress and actual completed receipts, and ends when the selected inventories finish or the 150-second UI request deadline is reached. Remaining work continues automatically in the service; no false success is reported for merely clearing discovery backoff.

BLE still discovers and authenticates the peer. Two upgraded peers negotiate an optional same-Wi-Fi bulk connection over an encrypted REP/1 control channel. The listening peer opens a temporary TCP listener bound to its private IPv4 Wi-Fi address. The initiator accepts only literal addresses on the same local private subnet; both sides authenticate the same BLE identity on the new channel and explicitly commit the handoff. No LAN invitation, private capability or raw inference endpoint is used. If local networking is unavailable (including AP isolation), continue on BLE. The listener is closed after negotiation. Sessions are bounded to 120 seconds, with a partial wakelock during active transfer. Negotiated Wi-Fi sessions can receive up to 4096 new items and inspect 65536 IDs in one direction; negotiated BLE sessions receive up to 128 and inspect 2048. Older peers retain the previous budgets. Pending inventory triggers expedited, jittered reconnection; saved cursors and durable receipts allow multiple sessions without manual intervention. Pending receipts are retained in the Tree before advancing their cursor. The UI reports a pending scan if the peer is unreachable or the receive deadline expires.

The bulk route is session-local; persistent independently resolvable public routes and Internet Axon transport are not implemented by this change. Same-Wi-Fi bulk handoff, BLE continuation, explicit LAN receives and both old/new protocol combinations require Android device validation.

## Windows desktop public Axons and IP discovery

The normal LAN-enabled `launch.cmd` starts automatic public Axon discovery and receive on the Windows host. It attempts to build the optional Windows-targeted BLE GATT reader independently; a failure does not prevent IP discovery or translation startup. `--local-only` disables network discovery; `ROOTS_PUBLIC_AXONS_DISABLED=1` disables only public Axons. Private LAN invitations and inference permissions stay separate.

Updated Android encounter services expose a GATT characteristic 7d6f6f74-732d-4c45-9a01-000000000004 (IPv4 address, unsigned network-order port, SHA-256 SPKI identity; 38 bytes) and answer bounded local-subnet UDP broadcast queries on 8235. Requests are ROOTS-AXON/1 followed by a space and 32 lowercase hex nonce characters; replies append a space, 64-hex identity and space 8235. A route is an untrusted discovery hint. Desktop restricts dialing to private local IPv4 subnets; it verifies the claimed identity via the authenticated REP/1 P-256 handshake on dedicated TCP 8235. No private token or administrative API is exposed. Android uses a shared session gate for BLE and direct LAN synchronization.

Windows enumerates active private IPv4 subnets, sends directed broadcasts, and periodically reads the BLE route characteristic via WinRT. It does not sweep every IP or port. It binds each authenticated peer as a persistent wildcard subscription, automatically pulls its eligible published graph, and stores receipts and provenance in the desktop native Tree. The host reoffers received public receipts, not its own private local graph by default. The existing desktop browser Tree subscription list includes public peers; Block prevents automatic rejoin. The existing Receive action requests a discovery/transfer sweep and reports actual completed fragments. Automatic polling continues after the manual receive completes. LAN discovery works without BLE if broadcast responses reach the host. Windows WinRT does not expose the Android LE L2CAP CoC socket API; this implementation needs a reachable shared local IP route for desktop bulk transfer, including BLE-discovered phones. BLE-only desktop transfer and persistent Internet routes remain future work. Android/Windows builds and device interoperability testing are still required.
