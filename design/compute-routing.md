# Capability-based compute routing (v1)

The phone does not determine physical location, SSID or BSSID. It uses the configured bridge address as a locator and the already paired 256-bit key as the device identity. On active Wi-Fi it sends an encrypted, text-free capability probe; an authenticated response advertises the compatible PLaMo translation model. The proof is cached briefly per network, address and pairing. The automatic route never falls back to the legacy plaintext bearer endpoint. AES-256-GCM uses HMAC-SHA256 direction-separated keys, random 96-bit nonces and request-bound responses. The host rejects stale/replayed requests within a bounded in-memory window. Clock synchronization is required. The pairing key must be kept secret; rotate it if previously exposed on plaintext networks. Legacy endpoints remain for existing clients. This is an application-layer paired protocol, not audited TLS.

The routing policy learns end-to-end completion latency in four input-size buckets, samples unmeasured/stale alternatives on authorized work, and uses a 10% threshold for desktop preference. No duplicate speculative requests. On-device PLaMo remains the default, and is the fallback if the paired host is unreachable, outdated, unauthorized or fails. If local inference fails and an authenticated desktop is available, it can fall back there. The desktop checkbox is permission for automatic routing, not a force-desktop switch. Existing FunctionGemma/poetic calls remain local: the desktop currently advertises only translation. No discovery across arbitrary IPs or multi-host load balancing; configure the bridge URL (a stable DNS hostname or DHCP reservation is useful). No captured text is included in the probe. No location permission.
